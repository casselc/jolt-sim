## `casselc/db` PR #2 — prove-clean-or-poison

Notes from the `perturb` research lane in `casselc/jolt-sim` (`docs/research/PERTURB-DESIGN.md`), offered not requested. We read this PR looking for things that contradict our design record — two did — and this is the return direction.

**1. Five well-formed recovery branches that no executed test reaches, and `jolt-sim` already owns the lever that would reach them.**

`docs/findings/begin-boundary-recovery-evidence.md` records honestly that **R3** — rollback claims success but `sqlite3_get_autocommit` still reports `ac = 0` — "is defensive coverage, not exercised by an executed test". R4, R5 and R7 are in the same position, and those are the *poison* branches.

`jolt-sim`'s SQLite model has the lever: `:tx-effect :when :always` (`src/jolt/sim/sqlite.clj:704-717`) applies the physical transition **even when the step reports its error**, and `:never` withholds it. That is an uncertain `BEGIN` on demand — exactly the state a real engine will not produce for you. Driving this contract from the simulated adapter and asserting each of R1–R7 is reached looks like the cheapest positive control available to either repo, and needs no new machinery on either side.

Our version of the rule, for what it is worth: a monitor that has never fired is not evidence, and every monitor needs a positive control.

**2. The `:cleanup-errors` bug has a general shape, and the test for it does not exist in either repo.**

`:cleanup-errors` is a ghost variable in all but name — cleared at attempt start, appended on failure, and consulted by `poisoned-transaction-exception` as `(:error (first errors))`, i.e. a precondition on a terminal edge. That precondition was **false** until review caught the missing clear, so a stale error from a *previous* attempt could be reported as the cause of this poisoning.

Our refinement syntax has an `:init` key for exactly and only this reason, and the defect it exists to prevent is the one that happened here. Generalisable without any of our machinery: **any accumulator consulted by an error path needs an explicit clear at attempt start, and the test for it is two attempts where the first fails differently from the second.**

**3. Two things this code taught us, recorded as corrections to our own record.**

- The pre-probe (**R6**) refuted a rationale of ours. We had argued that a validating runtime guard is always a deferred static check in disguise. No checker of the Clojure program can ever know SQLite's autocommit flag — there is a class of runtime guard that is not a deferred static check, and our stated reasoning did not distinguish it.
- `verified-sqlite-begin!` is a typestate machine written by hand, and **our declaration language cannot express it** — not because of the edge out of an uncertain state, which we can already say, but because one operation has three destinations chosen at run time. That is now the first evidence from outside our own code for a language feature we had listed as optional.

## `casselc/jolt-tcp` PR #2 — Windows triage lead

A lead on the Windows failures, from the `perturb` research lane in `casselc/jolt-sim`. **Unconfirmed** — CI logs were not reachable from the session that produced this, so it is argued from source only. Offered because it points one layer down, where it would be much cheaper to diagnose.

**The clock migration looks exonerated, with evidence.** `monotonic-clock-facts!` (`jolt-net/test/jolt/net/check.clj:71-90`), including its not-millisecond-truncated discriminator, is invoked by all four Windows gates — `blocking_test_main.clj:265`, `nonblocking_test_main.clj:445`, `wsapoll_test_main.clj:683`, `poller_wake_test_main.clj:691` — and `jolt-net` #2 is green on both Windows arches at the same pin.

**What changed is scope.** Both Windows jobs went from *negative* gates (require `net/open-poller` / `target/descriptor` to throw `:unsupported-target`) to *positive* ones, and x86-64 now runs `public-client-loopback-contract`, which starts a full `teensyp.server` reactor.

**The seam we would look at first (x86-64).** `teensyp.server/interest` (`server.clj:883-888`) returns `#{}` whenever `READ-MASK` is set — which includes `WORKING` — so **a live `WSAPOLLFD` entry with `events == 0` is a steady state for every connection while its handler runs**. `reconcile-shutdown-registration!` (`:1097-1100`) does the same explicitly. Meanwhile `readiness.clj:93-101` asserts for *both* targets that error/hangup "are never requested… Winsock additionally rejects them as inputs" — which relies on POSIX reporting `POLLHUP`/`POLLERR` regardless of `events`. `jolt-net`'s own `PLATFORM-COVERAGE.md` flags precisely this as divergent: a peer FIN with no pending data reports `POLLHUP` **alone** on Winsock.

The passing `jolt-net` W4 gate **never registers an empty interest set** and **never uses the 3-arity `await-ready` cursor form** — both of which the reactor uses (`server.clj:989`, `:1166`).

**Concrete suggestion:** add those two cases to `jolt-net`'s Windows gates. If the hypothesis holds, the failure reproduces one layer down where it is far cheaper to diagnose than inside a reactor loop. If it does not reproduce, the hypothesis is dead — also worth knowing.

**ARM64 we have no hypothesis for.** That lane never starts a server, so the above cannot explain it, and its assertions check out statically (`target.clj:181` makes `windows-aarch64` literally `windows-x86-64`, `:evidence :probed`). The only remaining candidate noticed was the jolt-hegel bump: `PLATFORM-COVERAGE.md` states Windows ARM64 has no property-test coverage and has never resolved that dependency, while the `:windows-arm64-preview` alias requires it with `JOLT_HEGEL_REQUIRED=1`.
